# Cómo meter v0.3.0 en tu repo

Guía para pasar de `master` (lo que tienes desplegado) a `development` con todo esto dentro.
Los cambios están hechos **sobre tu código real**, no sobre suposiciones: encajan con
`src/db/schema.ts`, `src/actions/index.ts` y tus clases de Tailwind tal como están.

---

## 0. Antes de nada: Node.js

Sigue siendo el paso que bloquea todo lo demás. Sin Node no puedes arrancar el proyecto ni
comprobar nada de lo que viene a continuación.

- Instala Node 22 desde [nodejs.org](https://nodejs.org) (la versión LTS).
- Comprueba: `node --version` tiene que responder `v22.x`.

**El proyecto nunca se ha compilado.** El primer `npm install && npm run build` va a sacar
cosas: son errores de la 0.2.0 saliendo a la luz, no de estos cambios. Hazlo **antes** de
aplicar nada, para saber qué es de quién.

```bash
git checkout master
npm install
npm run build      # ← esto es la línea base. Apunta lo que falle.
```

## 2. La base de datos

`npm run db:push` lee `src/db/schema.ts` y cuadra Neon con él, así que las columnas y la tabla
nuevas las pone solo:

```bash
npm run db:push
```

Pero **los `CHECK` no salen del esquema de Drizzle**, y uno de ellos importa. Pega
`drizzle/0001_v0_3_0.sql` entero en el SQL Editor de Neon. Es idempotente: si lo ejecutas dos
veces no pasa nada.

Por qué importa ese CHECK: `setLadderElo` es una Server Action, o sea un endpoint público. El
formulario acota el rango a 1500–2000 y la acción lo vuelve a acotar, pero cualquiera con la
consola del navegador abierta puede llamarla con `99999`. El CHECK es la tercera red, y es la
única que no depende de que el código esté bien.

Al final del fichero SQL hay tres consultas comentadas para comprobar que todo está.

## 4. Qué mirar en el navegador, y en este orden

1. **`/torneos/<un torneo>`** — arriba tiene que salir «Tus rondas». Apunta una ronda en modo
   rápido: rival, mazo, «Salí 1.º», «Gané». Guarda y comprueba que el récord de arriba cambia a
   `1-0-0` **y** que en «Resultados del grupo» tu récord también.
2. **La misma ronda otra vez, con el mismo número.** No se tiene que duplicar: se sobrescribe.
   Eso es el índice único.
3. **Modo juego a juego**: marca el juego 1 y el 2 con la misma letra. El juego 3 tiene que
   desaparecer solo en cuanto hay mayoría.
4. **`/perfil/<tú>`** → «Rango del ladder». Mueve la barra y guarda. Luego mira `/ranking`, al
   final: tiene que aparecer en el ladder.
5. **`/`** — las tres pestañas del panel. Pulsa un chip de la leyenda del Elo para esconder a
   alguien, y dos veces para quedarte solo con esa persona.
6. **`/torneos`** — los chips de filtro por persona. Comprueba que la URL cambia a
   `?jugador=...` y que la vuelta atrás del navegador funciona.
7. **`/ajustes`**, al final — «Zona de riesgo». **No pulses nada todavía.** Solo comprueba que
   aparece si eres propietario y que no aparece si entras con una cuenta de jugador.
8. **`/entrar`** en una ventana de incógnito → el enlace «Únete con tu código de invitación».

## 5. Desplegar

```bash
git add -A
git commit -m "v0.3.0: rondas de torneo, ladder, gráficos y borrados"
git push -u origin development
```

Vercel te crea un despliegue de vista previa de la rama. **Ese enlace pide cuenta de Vercel a
propósito** (es la Standard Protection), así que pruébalo tú desde tu cuenta y no lo mandes al
grupo. Cuando funcione:

```bash
git checkout master
git merge development
git push
```

Y entonces sí, el enlace bueno es el dominio corto de producción.

## 8. Decisiones que conviene no volver a discutir

**Las rondas no tienen tabla propia.** Una ronda es una fila de `matches` con `tournament_id` y
`round` — columnas que ya tenías. El motivo no es ahorrar una tabla: es que la matriz de
emparejamientos, el %V por arquetipo y la ventaja de empezar ya leen de `matches` + `games`, y
el ranking y el Elo ya ignoran las partidas con `player_b_id` nulo. Una tabla aparte habría
obligado a duplicar seis cálculos y a mantenerlos sincronizados para siempre.

**Dos columnas nuevas en `matches`, y por qué.** El modo rápido apunta el resultado de la ronda
sin desglosar juegos, así que no hay ninguna fila de `games` donde meter ni el resultado ni
quién salió primero. De ahí `series_result` y `first_turn`. La regla es que **los juegos siempre
mandan**: si alguien completa el desglose después, el marcador pasa a contarse y esas dos
columnas se dejan de mirar. Nunca hay dos verdades.

**El caso que casi se me cuela**, y por el que hay una casilla de «se acabó el tiempo»: un 1–1
en un Bo3 esperando el tercer juego y un 1–1 con el tiempo agotado tienen **exactamente los
mismos juegos apuntados**, pero uno es una ronda a medias y el otro un empate. Sin decirlo, el
código no puede distinguirlos. Hay una prueba dedicada a esto en `tests/rounds.test.ts`.

**El ladder es aparte del Elo.** Está en otro bloque del perfil y en otra tabla del ranking a
propósito. Si se mezclaran, el primer malentendido garantizado sería pensar que el rango también
se calcula.

**Los límites de best finish son de casa, no los oficiales.** 4 Challenges, 4 Cups y 5
Regionales. Están en el campo `bfl` de las tablas de `src/lib/cp.ts`, y hay una prueba que lo
fija en las dos temporadas para que un cambio accidental salte.

**Sin dependencias de dibujo.** Los gráficos son SVG y React a secas. No es purismo: meter
Recharts es un `npm install` más en un proyecto que todavía no ha compilado nunca, y podía
fallar antes de que el resto llegara a funcionar.

**Cuatro Challenges y cuatro Cups, por separado.** Dijiste «4 mejores resultados de challenges y
cups», y lo he leído como 4 de cada uno. Si querías 4 **entre los dos juntos**, es una línea:
en `src/lib/cp.ts`, ponle `"sharesBflWith": "league_cup"` a `league_challenge` en las dos
temporadas. La prueba «los límites de casa son 4 Challenges, 4 Cups y 5 Regionales» te avisará
de que la has cambiado.

  simulados (sin `node_modules` no se puede compilar entero).
- Un comprobador estático sobre los 67 ficheros: cada `import` apunta a un módulo que existe y
  que exporta ese nombre; ninguna `action={...}` referencia algo que no sea una Server Action
  exportada; nada exportado del fichero `"use server"` que no sea `async`; todo componente con
  estado o eventos declara `"use client"`; ningún `<form>` anidado; y todo `href` interno tiene
  su página.
- Las URLs de imagen de carta, contra el patrón real del CDN de Limitless
  (`TWM_130_R_EN.png`), incluidos el relleno a tres cifras, los sufijos de letra y los sets
  promocionales.
- Los colores de los ocho tiers, medidos contra tus dos fondos reales (`--ground` en claro y en
  oscuro). Todos pasan de 4,5:1. Plata, oro y platino los tuve que oscurecer: a ojo no llegaban.

**No comprobado, y no puedo desde aquí:**

- **`npm install` y `npm run build`.** No hay red en este entorno. Es el riesgo real que queda.
- **Nada se ha renderizado nunca.** La lógica está probada, el CSS no. Espera tener que ajustar
  espaciados en el móvil.
- **Ninguna consulta se ha ejecutado contra Postgres.** El `onConflictDoUpdate` de
  `syncTournamentRecord` va contra el índice único `tr_unique_idx`, que ya existía, así que
  debería ir; pero es SQL que no ha corrido.
- **El patrón de URL del CDN de Limitless** está verificado contra ejemplos reales, pero es de
  un tercero y puede cambiar. Por eso cada carta que no cargue cae a su línea de texto en lugar
  de dejar un hueco.
